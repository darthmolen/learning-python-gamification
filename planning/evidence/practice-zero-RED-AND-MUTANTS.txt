THIS WAS THE FIFTH REFUSAL AND THE PLAN DID NOT PREDICT IT. It is also the worst of them: it
rejects the tick before the database is ever consulted, so the failure a learner would have met

A THING THE TEST FOUND THAT IS NOT A BUG IN THIS CHANGE
---------------------------------------------------------
The first version of "still refuses a negative practice number" asserted `statusCode === 400`
and got 200 with this body:

    { "code": "verifier-failed",
      "message": "an area is 0-7 and a practice number is 0 or more",
      "retryable": false }

The guard fires; the status is 200 because `errors.ts` maps `verifier-failed` to 200 on purpose
-- it means "your submission did not pass", a domain outcome rather than an HTTP fault.

Using it for a malformed route parameter is a pre-existing oddity on this route (the `area`
bound has always answered the same way) and is left alone. Changing which code the route raises
is a contract change and belongs to whoever owns that table. The test now asserts the error code
rather than the status, and says so at the assertion.

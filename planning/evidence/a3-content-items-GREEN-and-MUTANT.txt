THE SHARED PROBLEM

Every one of these quests is about a program ANSWERING from its data rather than
remembering an answer. A test comparing output to a fixed transcript passes a
hardcoded submission, which is the exact thing being rejected. Reading source for
`len(` or `.get(` rewards the token, not the behavior.

So each test does self-consistency first, then SUBSTITUTION: change the data in a
copy of their program and require every answer to follow. Nothing ever writes to
the repository it was given.

  the-inventory      add a sixth item; count, last and numbering must all move
  pick-it-up         replay their own moves against their own start list
  the-hotbar         add three at the END, and rename the FIRST
  the-recipe         stock the missing ingredient; short empties, verdict flips
  what-am-i-missing  no substitution needed -- three set answers check each other

TWO MUTANTS THAT DID NOT BEHAVE, AND WHAT THEY TAUGHT

**the-hotbar: a hardcoded hotbar survived the growth check.** Adding items to the
END of the list leaves the first nine unchanged -- which is exactly what the check
asserts of a CORRECT program. A literal list of nine words is unchanged too, so
the two were indistinguishable.

Fixed by adding a second substitution that renames the FIRST item. A slice
follows; nine typed words do not. Recorded because the original growth check
looked obviously sufficient and was not, and only seeding it showed that.

**pick-it-up: `backpack.pop(1)` in place of `backpack.remove("bread")` survived,
and should have.** At that moment index 1 IS "bread", so the resulting list is
identical and the `- bread` label still tells the truth. The test asserts
observable outcomes, and this substitution has none. Checking WHICH method was
called would mean reading their source, which every one of these tests refuses
for good reason.

Proven not to be a hole: a mutant where the LABEL and the ACTION disagree --
printing `- rope` while removing bread -- is caught, naming the move:

    after move 2 (`- rope`) the backpack holds ['torch', 'bread', 'flint'],
    but the program printed ['torch', 'rope', 'flint'].

A mutant that survives for a good reason is a statement about a test's scope. One
that survives for a bad reason is a hole. These are one of each and the
difference is worth writing down.

TWO BUGS IN MY OWN TESTS, FOUND BY RUNNING THEM

**`\s*` crosses newlines.** `^short:\s*(.*?)\s*$` on an EMPTY `short:` line
consumed the newline and matched the next line's content, so a correct submission
failed with "could not read 'can build: yes'". Every brief here allows an empty
value -- an emptied backpack, a short list, nothing missing -- so this was live in
four files. All label patterns now use `[ \t]*`, which cannot leave the line.

**the-recipe stocked the wrong dict.** The first `{` after the first `=` is the
RECIPE, not the inventory. The fix identifies the dict by its CONTENTS -- the keys
the program itself printed -- which is the one identification that does not
depend on guessing what the learner named their variables.

Both were caught by the correct submission failing, not by a mutant. A test that
has only ever been run against wrong answers has not been tested.

THE LEDGER FIRED TWICE IN ONE DAY

`fixtures-agree.test.ts` went red at one quest and again at six:

    API []  ->  API [a3-the-inventory]  ->  API [a3-pick-it-up, ... six ids]

Then a THIRD time, with a new entry: `area 3: progress.total — fixture 5, API 6`.

That third one found something real. `area-3.yml` still said `estimatedQuests: 5`
with six quests authored. The engine takes `Math.max(estimatedQuests, authored,
cleared)` while `authoring: partial`, so the API had already answered 6 and
nothing was broken -- but the file is read by people, so it was corrected to 6
with the reasoning written in.

The fact being recorded ("the fixture names quests that do not exist") never
changed. The sentence carrying it was rewritten three times. That is the argument
for `planning/feature_the-fixture-ledger-compares-facts_2026-09-06.md`, made by
events rather than by assertion.

NOT PROVEN, AND IT CANNOT BE HERE

every `local-repo` test in the campaign carries, in the same line of code. The
first real submission is the check, and it is a check for the DM.

HOW A TEST JUDGES A PROGRAM IT HAS NEVER SEEN

The boss keeps state: it is asked a question, changes what it holds, and is asked
again about the thing it just changed. A transcript is useless twice over -- the
learner picks their own recipes, and the right answer to the second question
depends on what the first one did.

So the tests INTERVIEW the program first. `recipes`, then `recipe <name>` for
each, then `have`. That is the learner's own world in their own words, and every
later assertion is arithmetic over it. Nothing in the file has an opinion about
what a torch costs.

MUTANTS

  half-spending on a refused craft   CAUGHT by test_a_refused_craft_spends_nothing
      "the craft was refused and the inventory changed from {...} to {...}.
       Nothing is spent on a craft that failed -- check everything first, then
       spend."
      This is the bug the brief names as the one most people get wrong, and it is
      the one worth waiting for on the night: the program refuses correctly and
      has already broken the world, with no error anywhere.

  the crafted item is never added    CAUGHT -- ingredients spent, nothing gained
  ingredients are not spent at all   CAUGHT (2 tests)
  can always says yes                CAUGHT
  spends one of each, not the recipe CAUGHT

Each was checked for failing on the RIGHT test, after the earlier lesson that a
mutant failing for the wrong reason has not exercised the check it was aimed at.

TWO SCENARIOS THAT SKIP RATHER THAN PASS

`crafting twice` and `can changes its mind` cannot be built from every legitimate
world -- an inventory that affords two of everything is a valid submission. Those
return early rather than asserting something false. Recorded because a test that
silently does nothing is the failure this repository keeps finding, and a skip
that is invisible is the same thing wearing a tie.

WHAT NO TEST HERE CAN DO

§5.3's clean-clone rule. `dm-guide.md` §9 is the checklist, and it says explicitly
which failures count: a program that crashes on `craft banana` has not broken a
rule the brief fixes, and the DM says so out loud and lets the learner decide
whether to care.
